Get started in 3 steps

Loom keeps your session context so agents don't re-read everything. Here's how to use it.

1

Store — cache your context

Call ctx_store with a large output (command, file, analysis). Loom splits it into chunks and indexes it.

ctx_store(content, session_id, label="session/type/name")
2

Search — retrieve without re-reading

Before re-reading a file, search first. You get the chunk by ID instead of re-injecting the whole text.

ctx_search(query, session_id) → chunk_id
ctx_get(chunk_id)
3

Observe — watch the savings

This dashboard shows calls, latency and tokens saved live. That's your proof of gain.

💡 Golden rule: if an output exceeds ~100 tokens, store it. If you already read it, search before re-reading.

How-to — common tasks

Copy-paste recipes for frequent cases.

📥 Store a terminal output

A build, a scan, a large log: send it to the cache with a clear label.

ctx_store_cmd(cmd, output, session_id)

📄 Store a file

Before analyzing a long file, cache it once.

ctx_store_file(path, session_id)

🔍 Retrieve a chunk

Semantic search (meaning) with automatic text fallback (FTS).

ctx_search("firewall rule", session)

🔗 Transfer between sessions

Reuse a chunk from another session without copying it.

ctx_transfer(chunk_id, target_session)

🧹 Purge / clean up

Remove a session or expired chunks (TTL), then compact.

ctx_purge_session(sid)
ctx_purge_expired() · ctx_vacuum()

⚙️ Rebuild the vector index

After a large import, regenerate the HNSW index for semantic search.

ctx_rebuild_index()

Help — glossary & FAQ

What the numbers and words in the dashboard mean.

Glossary

TermDefinition
SessionA thread of work (conversation, task). Each session has its own context.
ChunkA piece of stored content. It's the base unit of the cache.
AnchorAnchored version of a chunk: the compressed/summarized text that replaces the original.
Savings% of tokens saved = (tokens before − anchored tokens) / tokens before. Higher is better.
InvariantA stable value detected in the content (constant, key, hash) — can be verified later.
Hit / MissHit = the cache served the content (no re-computation). Miss = absent, it had to be produced.
Hit rate% of calls served by the cache. Goal: as high as possible.
p50 / p95Latency: p50 = median (half are faster), p95 = the worst 5%.
FTSFull-Text Search — keyword search, used as a fallback for semantic search.
HNSWA fast vector index type, to retrieve chunks by their meaning.
T0 / staticContent never reloaded (0 tokens per turn), so free to reuse.
WALWrite-Ahead Logging: SQLite mode that avoids blocking on concurrent writes.

FAQ

Why is my savings % low?

The cache is empty or underused: store more outputs and search before re-reading. The % rises once chunks are reused.

p95 latency is high (e.g. 30,000 ms), is that bad?

A high p95 = a few very slow calls (large payloads, first embedding-model load). Look for a token spike or a heavy write at the same moment.

Difference between ctx_store and ctx_search?

store writes to the cache, search reads from it. Store once, search as many times as needed.

Are my chunks indexed for the vector store?

View Upgrade P1-P3 → Coverage card. If < 100%, run ctx_rebuild_index().

How do I know if the cache works?

View Overview: the Savings donut and the Hit rate card. High savings + high hit rate = effective cache.
